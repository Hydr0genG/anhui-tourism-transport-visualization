# 采集数据源与爬虫架构建议

调研日期：2026-10-14。本文是设计建议，不表示已接入外部 API、补齐数据或完成入库。本轮没有修改业务代码、来源启用状态和数据库。

范围更新：用户已要求扩大到黄山以外。本文的四实体范围保留为首批原型背景；后续采集对象、来源扩展和阶段安排以 [23-安徽多城市数据采集扩展计划.md](./23-安徽多城市数据采集扩展计划.md) 为准，本文的原件追溯及入库原则继续适用。

## 1. 范围与结论

沿用当前四个实体：黄山风景区主景区、黄山北站、黄山屯溪机场、合肥新桥机场。以 2023 年至最新已发布统计期为主要回补窗口；更早历史可独立补充，不能代替近期覆盖。未来扩展全省时按实体登记逐项增加。

建议建设“多来源采集与入库流水线”，复用现有 Python、SQLAlchemy、Alembic、MySQL 数据层。公开报表是核心客流的主要已知来源，API 主要补充气象、预警和地理信息。连续景区/铁路实绩仍需进一步查找公开数据或取得提供方的数据接口、报表。

“完整”按实体×指标×统计范围×粒度×时期验收，不能只按抓到的网页数量验收。区分公开发布后尚未采集、来源尚未发布、来源不提供该粒度、抓取失败、解析失败、待核验六种缺口。

## 2. 现有基础与缺口

依据 `real_data/2026-10-12-v2/quality_report.md`，已有 83 条普通观测、17 条补充事实、26 个全国假期窗口、16 份知识资料。两机场各有 41 个月值，缺 2023—2025 年的 12 月，最长连续段为 11 个月。铁路普通观测只有一个日值；景区尚缺可用的连续主景区月度序列。

代码已有标准 CSV 导入、真实资料包导入、原件登记、修订记录、质量问题、覆盖查询、作业领取/租约/心跳/恢复。`examples/fetch_real_dataset.py` 是已有公开原件获取基础；`sources` 仍关闭自动更新，`adapter_key=standard_csv` 不代表已实现各网站自动采集。

| 名称、地址、经纬度、别名 | 运营方官方资料；必要时使用地图 API | 静态主数据 | 统一实体，记录坐标系及地点含义 | 四个实体已有，坐标尚待核验 |

主要核验入口：

- [民航华东局统计栏目](https://hd.caac.gov.cn/HD_XXGK/HD_TJSJ/)；本轮检索确认了[2026 年 7 月统计发布页](https://hd.caac.gov.cn/HD_XXGK/HD_TJSJ/202608/t20260824_231576.html)。栏目直接打开失败不等于来源失效；已有原件证据仍保留，自动采集上线前要验证 HTTP 可达性。
- [黄山旅游 2025 年年度报告](https://static.cninfo.com.cn/finalpage/2026-04-18/1225118314.PDF)，明确区分进山游客与索道、缆车运送量。季度/年度事实暂按现有资料包保留，不能强写成月度观测；如需查询，后续单独扩展粒度契约。
- [黄山北站 2026 年清明发送量公开报道](https://www.huangshan.gov.cn/zfsj/sjjd/8420396.html)，属于零散假期/日数据，且存在“余”字近似表述，不直接转为精确数值。
- [国务院年度放假安排通知](https://www.gov.cn/zhengce/zhengceku/202511/content_7047091.htm)。
- [黄山市政府数据入口](https://www.huangshan.gov.cn/zfsj/index.html)列有数据集与接口资源入口，但本轮没有核实覆盖这四个实体连续客流的具体数据集、接口参数和权限，暂列候选。

新发现的历史候选：[管委会公开材料](https://hsgwh.huangshan.gov.cn/zwgk/public/6617641/11352697.html)的搜索索引列有“表 2.2-1 景区近五年接待游客数量统计表”，覆盖 2017—2021 年逐月数据，理论上有 60 个历史月值。本轮直接打开原页失败，因此仅登记线索；取得原件、确认实际统计范围、核对全年合计后才能入库。不用搜索摘要当原件，也不以旧序列宣称近期数据已齐。

## 4. 外部 API 选型

| API/数据服务 | 是否必需 | 接口或数据产品 | 关键输入和输出 | 凭证及限制 |
|---|---|---|---|---|
| Open-Meteo 历史天气 | 气象辅助预测可选 | `GET https://archive-api.open-meteo.com/v1/archive` | WGS84 经纬度、日期范围、daily/hourly、timezone；温度、降水、风速等 | 接入前确认对应使用场景的服务额度与许可；是再分析产品，不冒充站点实测 |
| 中国气象数据网 | 历史站点实测候选 | 中国地面气候资料日值数据集 V3.0 等 | 站点、日期、温度/降水/风等 | 具体站点覆盖、最新数据范围及账户下载权限待核验；未确认通用匿名 API |
| 和风天气预警 | 当前天气预警功能建议接入 | `GET /weatheralert/v1/current/{latitude}/{longitude}`，使用账户 API Host | 经纬度；预警 ID、发布单位、生效/到期、更新/取消关系 | 需要账户凭证，建议 JWT；额度、存储及展示条件按账户确认 |
| 和风天气实况/预报 | 天气展示或未来天气特征可选 | 采用现行天气 API 文档的实况/每日预报产品 | 坐标、预报时段；温度、降水、风等 | 与历史天气分开保存；保留预报发布时间和目标时间 |
| 高德 POI 2.0 | 地图定位辅助可选 | `GET https://restapi.amap.com/v5/place/text` | `key, keywords, region, city_limit`；POI ID、名称、位置、区划 | Web 服务 Key；四个固定对象可低频核验，确认保存和展示条件 |
| 高德地理编码 | 有地址时可选替代 | `GET https://restapi.amap.com/v3/geocode/geo` | `key, address, city`；坐标、区划、匹配级别 | 同上；跨地图/气象服务使用时必须识别和转换坐标系 |
| 景区/铁路提供方接口 | 若要求连续实绩则重点争取 | 待提供方给出接口文档；也可采用定期 CSV/XLSX/SFTP | 实体、日期、统计范围、实绩值、单位、修订版本 | 未取得权限和文档，不能预设接口地址或可用性 |

API 依据：[Open-Meteo 历史文档](https://open-meteo.com/en/docs/historical-weather-api)、[中国气象日值产品](https://m.data.cma.cn/data/detail/dataCode/SURF_CLI_CHN_MUL_DAY_V3.0.html)、[和风天气预警](https://dev.qweather.com/docs/api/warning/weather-alert/)、[天气产品](https://dev.qweather.com/docs/api/weather/)、[认证文档](https://dev.qweather.com/en/docs/configuration/authentication/)、[高德 POI](https://lbs.amap.com/api/webservice/guide/api-advanced/newpoisearch)、[地理编码](https://lbs.amap.com/api/webservice/guide/api/georegeo)。本轮核验的是文档，不代表已使用用户凭证完成调用。

两个选型陷阱：和风[时光机接口](https://dev.qweather.com/docs/api/time-machine/time-machine-weather/)只直接提供最近 10 天，不能用它一次补齐数年历史；其[弃用列表](https://dev.qweather.com/docs/deprecated/)已将旧 `/v7/warning/now` 标为 2026-10-01 停服，应使用当前预警产品。

[12306 官方服务说明](https://kyfw.12306.cn/otn/gonggao/onlineBooking.html)列举时刻、余票和正晚点等查询。这些信息不等于黄山北站实际发送人次，本轮没有核实到符合该统计需求的公开开发者 API。地图热度、航班架次、车次、票务库存也不能替代目标客流指标。

录像入口计数属于单独的数据生产链路，需要授权录像、入口位置、方向、计数线和人工标注，不能通过上述公开 API 补齐。

## 5. 推荐架构与职责

数据流：来源登记 → 调度入队 → 发现新资料 → 下载原件 → 解析候选记录 → 标准化与质量校验 → 事务入库 → 覆盖报告 → FastAPI 查询/预测/RAG。

| 层 | 推荐实现 | 与项目现有能力的关系 |
|---|---|---|
| 来源配置 | 每个站点/数据产品单独配置白名单、分页、粒度、实体映射、更新周期、解析版本 | 复用 `sources`，增加配置契约；不要长期把所有网站标为 standard_csv |
| 调度 | 一个独立调度进程，按来源生成幂等任务；支持首次回补、增量、指定缺期重抓 | 复用 `jobs/job_attempts`，D 负责运行；不要在每个 HTTP 进程各起调度器 |
| 采集 | Python HTTP 客户端 + lxml；动态页面必要时使用浏览器；PDF 使用已有 pdfplumber | 将现有 example 脚本中可复用逻辑整理为 C 的适配器，保留文件导入 |
| 原件 | 首期使用配置的 DATA_ROOT；按内容摘要保存 HTML/PDF/JSON，生产可改对象存储 | 复用 `source_assets`；下载和解析在业务数据库事务外执行 |
| 质量 | 实体、口径、周期、单位、精度、来源和重复/冲突校验；未知新格式隔离 | 复用 `quality_issues`；解析成功不自动等于已核验 |
| 入库 | 经工作单元调用仓储；业务键幂等，修订留痕，批次失败独立记录 | 复用 `observations/observation_revisions/ingestion_runs/series_policies` |
| 服务 | HTTP 从标准库查询；知识文档登记后另排索引任务 | 复用现有 C→D/E 契约；采集任务不在网页请求内同步执行 |

首期数据量可使用 MySQL 作业表协调任务，无需额外引入 Kafka、Airflow、MongoDB 或另换数据库。后续吞吐量实际超出能力时再选择消息队列。

建议适配器入口：`discover(cursor) -> references`、`fetch(reference) -> raw_asset`、`parse(raw_asset) -> candidate_records`；下游共用 normalize/validate/persist。它们是拟定接口，不是现有导出方法。

外部采集器通过内部 Python 仓储契约入库；现有 HTTP `POST /api/v1/jobs/ingestion` 和 `GET /api/v1/jobs/{id}` 供管理端触发与查看。项目 HTTP 文档是设计契约，本地尚不能据此宣称路由已实现。

## 6. 数据结构与验收规则

客流继续使用既有字段：`entity_id, metric_code, period_start, period_end, grain, value, unit, original_value, original_unit, conversion_factor, source_id, asset_id, source_locator, methodology_version, published_at, quality_status`，采集时间从原件/批次追溯。

新增采集状态建议保存：来源游标、最近检查和成功时间、ETag/Last-Modified（来源支持时）、解析器版本、失败类型及下一次可重试时间。可先扩展配置和运行元数据，迁移需求在实现设计时确认。

气象如果启用，应新增独立表或独立契约，记录位置/站点、坐标系、高程、数据类型（实测/再分析/预报）、有效时间、发布时间、变量、单位、来源和模型版本，避免混入客流指标。节假日的每日工作/休息属性需检查现有假期窗口是否足够表达；必要时新增日期维表。

必须执行：

1. 主景区、全域旅游、铁路发送、铁路到发、机场吞吐量分别保存，禁止混成总客流。
2. 区分本月、年累计、全年、预计和实际。“10 万余”等近似值保存限定语，不能当精确值。
3. 月报不能展开为周/日；年度不能平均拆月。沿用当前项目“不自动累计求差”规则。
4. 同一新闻转载多次只产生一个事实；不同来源冲突保留证据并复核，禁止按最后抓取结果无条件覆盖。
5. 原件 URL、摘要、页码/行/段落、发布时间和获取时间可追溯。来源内容更新时保留旧版。
6. 429/超时按上限退避重试，403/验证码/结构变化进入诊断或复核；不重复高频重试。失败不等于无新数据或零客流。
7. 预警按 ID、更新、取消、到期维护；接口失败或过久未更新时显示来源状态，不能把缺响应当解除。
8. 覆盖报告同时输出应有周期、已发布可采周期、已核验周期、最长连续段和缺期原因；预测以实际回测验证可用性。
9. 原件和字段的存储、展示范围按来源条件配置；公开可读与允许全文再发布分别记录。
10. 天气用于回测时，预报只能用预测截止时已发布版本，防止使用未来信息。

## 7. 建议采集频率与实施顺序

频率是建议值，需服从来源配额和发布规律：机场月报每周检查；景区/铁路统计每周检查，节假日专题期间每日检查；官方公告每 1—6 小时；天气预警每 10—30 分钟；历史天气首次回补后每日补最新可用数据，明确产品延迟；节假日每周检查新增通知，地理资料初始化及变更时复核。

实施顺序：

1. 固定四实体及指标口径，制作 2023 年至最新已发布期的逐月覆盖矩阵；确认每条候选来源的样本、原件、可达性与使用条件。
2. 将机场目录发现/附件解析接入作业链路，完成一条“下载→核验→入库→重复无新增→来源修订留痕”的真实闭环；保留十二月缺口清单。
3. 核验新发现的景区历史表，扩展景区与铁路官方统计/假期实绩采集；连续序列缺口登记提供方接口或文件需求。
4. 接入假期及官方公告；复用原件生成知识文档索引任务。
5. 按功能选择历史天气、预警 API 和地图定位；补对应表与凭证配置。
6. 开启增量调度和缺期重试，以覆盖率、可追溯率、数据新鲜度及失败恢复验收。连续客流仍未取得时，明确功能范围，不能把流水线运行成功称为数据已完整。

第一阶段无须购买商业客流 API 即可推进公开资料采集。若目标包含四实体连续日/周数据、可靠的近期预测或实时入口人数，提供方授权数据与录像输入仍是独立前提。
