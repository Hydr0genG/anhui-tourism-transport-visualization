# C 数据流程、运行方式与验收

设计版 0.2，2026-10-10。第一版已实现迁移、目录种子、规范 CSV 导入、质量摘要和本地测试；自动官方来源适配、完整周调度及备份恢复演练仍待后续实施。数据库见[字段字典](./03-数据库字段与关系字典.md)，调用方式见[契约](./04-DE调用契约.md)。

## 1. 一条客流数据的完整旅程

1. C 在来源台账登记发布方、使用依据、真实粒度、指标、覆盖范围及适配器；尚未核验的来源默认不启用。
2. 根据来源取得原文件/网页快照，计算 SHA-256，写入临时文件，校验后原子移动至受管理原件目录；同摘要复用现有原件。
3. 以短事务写 source_assets 和 ingestion_runs。网络获取失败也写失败批次，asset_id 可空。
4. 适配器把文件解析成候选行，定位原文页码/表格/行，不直接写 observations。
5. 标准化实体、指标、日期、单位和口径。保留原文值、单位、换算因子，不因图表需要改变时间粒度。
6. 校验每条候选：不合法的进入隔离记录；存疑但结构合法的标为 pending_review；核验通过的才能是 verified。
7. dry-run 只记录检查结果和预计变化；正式导入锁定该 source 记录，再按唯一键比较当前记录，完成新增/跳过/修订。
8. 观测修改、修订历史、问题记录和批次成功计数在一个原件级事务内提交；失败回滚，再用单独事务保存批次失败原因。
9. 生成覆盖与质量报告；D 查询已核验主序列，A/B 展示并保留来源。预测服务使用冻结输入快照。

文件系统和 MySQL 不能靠普通数据库事务实现共同回滚。处理原则是“文件先完整落盘，数据库再引用”：失败可能留下未引用文件，但不允许成功记录指向未完成文件。定期列出孤立文件，确认无引用后再清理；原件和旧索引不能按短期缓存自动删除。

## 2. 来源适配器协议

每个适配器只实现三个职责，避免将来源细节扩散进仓储：

```text
check(source, previous_state) → SourceCheck
  返回待获取链接/文件、是否可能有更新、检查证据

fetch(source, item) → RawArtifact
  返回临时文件引用、原文 URL、标题、发布日期、采集时间、媒体类型

parse(artifact, parser_version) → CandidateRow 迭代器
  返回原始实体/指标名称、起止、粒度、数值、单位、原文定位、口径说明
```

规范文件导入是第一个适配器：让经过人工核验的表格导出为约定格式后入库。第二个适配器再对接实际选定的官方来源。按每个来源单独写小解析器，不在截止日前建设通用爬虫平台。PDF/网页格式变化时标失败并保留旧数据，不把解析出的空列表当成所有历史数据都被删除。

规范导入至少包含：`entity_id, metric_code, period_start, period_end, grain, original_value, original_unit, source_id, asset_id, source_locator, methodology_version`。published_at 优先从原件取得；候选行声明与原件不一致时待复核。C 的 normalize 函数负责标准单位转换，不能要求每个来源各自决定。

HTTP 下载由来源登记限制目标域名及允许的重定向；只有管理员维护来源配置。D 的资料上传与远程采集分开，不把用户任意输入 URL 直接作为内部网络抓取目标。

## 3. 去重和修订的判定

| 情形 | 动作 |
|---|---|
| 已成功导入的相同原件＋相同 parser/normalize/quality 版本 | 记录本次无变化检查；新增数 0 |
| 原件相同但解析/质量规则升级 | 重新处理，业务唯一键继续兜底；不能仅凭文件摘要直接跳过 |
| 业务唯一键不存在 | 插入新观测，row_version=1 |
| 唯一键相同，数值/单位/口径/质量等业务内容相同 | 跳过；保留新检查批次，不把 ingested_at 刷成“新数据” |
| 唯一键相同，内容变化且已确认来源修订 | 当前完整记录写 revisions，再更新并递增版本 |
| 唯一键相同，内容变化但无法确认原因 | 隔离待审，旧 verified 版本保持可查 |
| 两来源发布同周期值 | 同时保存，按 series_policies 选择；未能选源则该期不进入默认主序列 |
| 来源网页删除历史行 | 记录变化待核验，不自动物理删除已有事实 |

同来源的两个并行导入先在最终写事务中锁住 source 行，再依唯一键查询/修改，避免同一修订写两次；下载和解析在锁外完成。数据库唯一约束是最后防线。死锁/并发冲突按整个短事务有限重试，不在已失败事务里继续写。

若同一事务需要检查任务和来源，锁顺序固定为 jobs → sources → observations，多个同类 ID 按固定顺序处理，减少互相等待。后台写入必须先验证当前租约，再写业务结果。

## 4. 质量检查与输出

| 检查 | 判定 | 处理 |
|---|---|---|
| 对象/指标 | 不存在或类型不匹配 | 隔离，不能进入 verified |
| 数值 | 非数字、负数、超出类型精度 | 隔离，不截断/改零 |
| 单位 | 无映射或“人数/人次”含义不明 | 待核验，保留原单位 |
| 日期 | 周/月边界错误、起止倒置 | 隔离；holiday 使用确切假期边界 |
| 来源 | 原件缺失、来源不明、原文定位缺失 | 待核验，不宣称可追溯 |
| 重复 | 同键同内容 | 跳过并计数 |
| 口径变化 | 定义、统计区域、范围变化 | 标断点，不能直接接成同口径序列 |
| 异常值 | 与相邻周期变化触发来源专用阈值 | 仅提示人工复核，不自动删除真实峰值 |
| 缺期 | 请求完整周期没有合格选源观测 | 报缺失；不是 0，也不插值 |
| 累计量 | 只公布年累计/节假日累计 | 保留其真实统计区间；首版不自动拆成月/日 |

首版只发布原生观测；跨粒度聚合、累计求差是后续可选能力，若开启必须记录公式和输入版本，并完成完整性检查。日/月均值可在 D 的比较响应中计算，但不是新增观测。

报告输出两种形式：结构化 JSON 给程序使用，Markdown 给组员检查。字段至少有 report_version、generated_at、数据范围、对象/指标/粒度、应有/可用周期、缺期、最长连续段、最大缺口、源冲突、异常记录、最新发布日期、原件可追溯率、待审数量、规则版本。质量报告不能写成“通过”而不列出真实缺口。

## 5. 每周更新与后台任务

运行进程只有：MySQL、D 的 FastAPI、D 的 worker，以及 A 的前端。C 不常驻启动第二个 API 或调度进程。D 的 worker 调用 C 的任务规划/执行函数，E 的分析同样由这个任务入口调度；首版只要求单个 worker 实例。

默认检查时间：每周一 09:00，Asia/Shanghai。已错过调度时段的来源在 worker 下次启动时检查最近应执行时段，依幂等键只补一次，不回放多年周任务。该时间可配置，来源实际只按月发布则无更新周 imported_count=0。

任务状态：

```text
queued → running → succeeded
                  → failed
running（租约过期）→ queued（未超重试次数）
running（租约过期）→ failed（已超重试次数）
failed → queued（管理员明确发起重试，保留历史尝试）
```

首版建议默认：租约 120 秒、心跳 30 秒、自动尝试最多 3 次；这些是可配置设计值，须在长视频实测后调整。worker 必须在独立于耗时推理的执行路径续约，不能等模型跑完才发心跳。

领取、恢复和发布时锁住 jobs 行，并检查 attempt_no/token/status/租约。在同一事务中更新当前尝试和作业；过期旧执行者即使恢复，也无法再提交成功结果。使用行锁的事务边界参考 [MySQL 锁定读说明](https://dev.mysql.com/doc/refman/8.4/en/innodb-locking-reads.html)。

采集幂等键分开计算：定时任务按来源集合、计划时段、dry_run；手动任务按 D 生成的请求标识、来源集合、dry_run；规范化 JSON 后计算摘要。dry-run 与正式执行不复用同一逻辑作业。视频任务键含原件和完整配置摘要；知识任务键含文档内容版本、索引配置和目标版本。一次任务可能涉及多个来源/文档，结果逐项记录。

## 6. 文件与目录运行规则

正式资产根目录由 DATA_ROOT 指定，建议开发时位于 `data_foundation/assets/`，部署时由 D 指定持久化路径：

```text
DATA_ROOT/
├── raw/<source_id>/<sha256>/original.<ext>
├── processed/<run_id>/normalized.jsonl
├── knowledge_sources/<document_id>/<version>/...
├── video_sources/<video_id>/...
├── permissions/<permission_id>/...
├── indexes/<document_id>/<version>/...          # E 产物，C 只登记
└── reports/<report_id>/...
```

同一原件只存一份，文档/录像目录可仅保存清单或受管理引用，避免无意义复制大型文件。数据库内部 FileRef 只含相对路径、摘要、媒体类型和大小。解析路径必须限制在配置根目录内，拒绝越界；D 不向浏览器返回绝对路径。

原件、授权证明、录像、向量产物、数据库导出和密钥不进入 Git；字典、台账中可公开的元数据、迁移、代码、测试样例和不含敏感信息的报告入 Git。现有根目录 `.gitignore` 已忽略部分原件目录，实施时 C 的 `.gitignore` 需补充 permissions/indexes 及运行期 reports 中的受限文件。

## 7. 配置与目标命令

| 配置 | 用途 | 拟定默认 |
|---|---|---|
| DATABASE_URL | MySQL 连接，由 D 的配置传入 C | 无默认，不保存真实凭据 |
| DATA_ROOT | 持久化资产根目录 | 显式配置绝对路径 |
| APP_TIMEZONE | 展示/调度时区 | Asia/Shanghai；库内仍存 UTC |
| WEEKLY_CHECK_SCHEDULE | D worker 检查时间 | 周一 09:00 |
| JOB_LEASE_SECONDS / JOB_HEARTBEAT_SECONDS | 租约与心跳 | 120 / 30 |
| JOB_MAX_ATTEMPTS | 自动重试上限 | 3 |
| QUERY_MAX_POINTS / MAX_IMPORT_ROWS | 查询/单原件限制 | 10000 / 100000 |

配置从 D 的 settings 或 C CLI 显式传入；C 包 import 时不自动读取未知目录的 .env，不自动连库、不自动建表。MySQL 连接池在 store 初始化，退出时 dispose。数据库不可用时应失败并给出简洁错误，不能偷偷切换 SQLite。

以下命令已在 v0.1.0 提供；正式执行前必须配置 MySQL 和真实资料：

```bash
# 从项目根目录安装 C 的可编辑包；使用团队约定的虚拟环境
python -m pip install -e ./data_foundation

# 运行前由环境提供 DATABASE_URL；配置文件应正确定位脚本目录
python -m alembic -c data_foundation/alembic.ini upgrade head

# 先检查连接/迁移/目录，再导入来源台账与指标字典
python -m data_foundation.cli doctor
python -m data_foundation.cli seed-catalog

# SOURCE_UUID 是真实台账 ID 的占位符；默认 dry-run
data-foundation ingest-csv verified-data.csv --source-id SOURCE_UUID --asset-id ASSET_UUID
data-foundation ingest-csv verified-data.csv --source-id SOURCE_UUID --asset-id ASSET_UUID --apply

# 导出覆盖和质量报告
data-foundation quality-report
```

CLI 与 D worker 走同一应用服务。CLI 导入也创建作业并领取租约，不能绕过幂等逻辑；seed-catalog 只登记基础目录，不创建默认密码或假业务数据。管理员创建继续由 D 的离线脚本负责。

## 8. 迁移、恢复和联调

- 数据库分开发、测试和联调库；合成样例仅进入测试库。业务 API 不提供“切到假数据”的开关。
- 首次联调交接包版本、Alembic head、数据字典版本和测试数据版本。启动 doctor 核对迁移，不允许缺表时自动凑一套表。
- Alembic 自动生成的是候选迁移，必须人工核查唯一键、外键、默认值和数据迁移；不能认为自动生成已经正确。依据 [Alembic 官方说明](https://alembic.sqlalchemy.org/en/latest/autogenerate.html)。
- 更新前备份数据库，并保留资产清单及对应文件；两者一起恢复才能追溯。首版维护窗口内暂停写入/worker，完成备份与迁移，验证后恢复运行。
- 不默认执行破坏性 downgrade。升级失败先停止服务、核对实际迁移状态，再修复或从备份恢复；MySQL DDL 不能被当作普通业务事务整体回滚。
- 17 日在空库重建，并在旧交接库副本验证升级；至少恢复一次数据库及其引用的原件，避免只备份数据库却丢失资料。

## 9. 验收矩阵

| 编号 | 场景 | 必须观察到的结果 | 阶段 |
|---|---|---|---|
| T01 | 从空库升级到 head | 所有表/约束建立，doctor 通过 | 12 日 |
| T02 | 重复导入相同数据 | 新增数 0，观测数不变，有检查批次 | 12 日 |
| T03 | 来源更正数值 | 当前值更新，旧版本可查，批次/原件不丢 | 12 日 |
| T04 | 错误对象、单位、月转周 | 明确拒绝或隔离，默认查询不污染 | 12 日 |
| T05 | 缺一期观测 | missing_periods 和覆盖率正确，不填零 | 12 日 |
| T06 | 会话到期/撤销、用户停用 | 有效会话查询返回 None | 12 日 |
| T07 | E 写入片段、计数、预测 | 按对应文档/分析/运行读回，输入输出一致 | 12 日 |
| T08 | D/E 对接样例 | 接收方环境可调用，版本已记录 | 12 日 |
| T09 | 写入中途失败 | 业务变更回滚，失败批次仍可查 | 14 日 |
| T10 | 两来源同周期冲突 | 不重复求和；选源明确或报告缺口 | 14 日 |
| T11 | 任务崩溃、过期旧任务恢复 | 可重试，旧 token 无法再发布 | 14 日 |
| T12 | 两次周检查/无新数据 | 不重复业务导入，状态和计数真实 | 14 日 |
| T13 | 索引新版本失败 | 老版本仍可引用；首次失败不伪装 ready | 16 日 |
| T14 | 计数重传/边界/不同值 | 同值去重，冲突拒绝，不重计边界 | 16 日 |
| T15 | 授权撤销或过期 | 不再开始新分析/回放；保留内部记录 | 16 日 |
| T16 | 预测输入超过截止时间 | C 拒绝保存不合规输入；算法质量由 D/E 验收 | 16 日 |
| T17 | 空库重建/旧库升级/备份恢复 | 数据与引用原件均可用 | 17 日 |
| T18 | 图表随机抽样追溯 | 至少 5 条或全部记录可找到原件及批次 | 17 日 |

第一版代码已覆盖 T01—T08 的本地自动化场景；其中 T01 使用 SQLite 执行迁移并额外离线编译 MySQL DDL，真实 MySQL 服务器上的迁移与 D/E 环境调用仍需共同验收。T09—T18 是 13—17 日继续实现和执行的检查。优先验证真实 MySQL 行为，不以只有 Mock 的测试替代数据库约束与迁移测试。

## 10. 开发切片与小白参与方式

**第一条链路：实体＋指标＋来源＋原件＋观测。**先让一个核验过的数值完整入库并查询到来源；这是你理解数据库的主线。此时同步交 D 用户/会话存储，不能让登录等待所有采集完成。

**第二条链路：D/E 依赖全部接通。**按四个迁移批次完成必要读写，特别是知识、录像、任务与预测结果；12 日交接时必须能实际调用。材料不足如实标记，测试样例不作为真实数据交付。

**第三条链路：数据自动更新与可复现。**13—17 日补来源适配、质量检查、调度恢复、资料标注、联调和备份复现。

你负责判断和学习：数据含义、单位、来源、样本核验、基本查询、验收结果。我可以协助编写模型、迁移、仓储、任务与测试；你不需要先独立掌握每张表的全部实现。每天以“今天有哪条可运行链路”为检查点，不以“生成了多少文件”作为完成度。

原计划 41—49 小时按已有基础估算，不适用于数据库零基础独立完成。暂不提供未经实测的新总时长；完成第一条链路后，用实际耗时调整安排。截止日不变时优先缩小真实对象/来源数量，保留完整追溯和核心依赖，不能靠删除验收环节赶时间。
