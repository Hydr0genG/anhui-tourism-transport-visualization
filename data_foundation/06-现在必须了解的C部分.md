# C 部分入门：你现在必须了解的内容

适用时间：2026-10-10 至首轮交接。面向数据库零基础。本文只保留你现在做决定、与组员沟通和验收时必须懂的内容。完整字段设计仍以[数据库字段字典](./03-数据库字段与关系字典.md)为准。

## 1. 先记住一句话

**C 的任务，是把有来源的原始资料变成可查询、可更新、可追溯的数据，再交给 D 和 E 使用。**

你不是负责制作页面，也不是负责预测算法。你负责保证页面和算法使用的数据是真实的、含义清楚的，并且能找到出处。

```text
官方网页、表格、公告、授权录像
                ↓
        C：登记、保存、清洗、检查、入库
                ↓
             MySQL 数据库
             ↙          ↘
     D：接口和登录      E：RAG 和录像分析
             ↓          ↓
              A/B：页面展示
```

如果页面上出现“黄山某月接待 100 万人次”，你应该能回答：

1. 这是哪个对象、哪个指标？
2. 统计的是哪段时间，单位是什么？
3. 来自哪个发布单位和哪一份原文？
4. 是哪一次导入放进数据库的？
5. 数据有没有缺失、重复或口径变化？

能回答这五个问题，就是 C 部分最核心的能力。

## 2. 你和其他组员的边界

| 成员 | 负责什么 | 你要给他什么 |
|---|---|---|
| A | 总览、景区、假期页面 | 经 D 提供的真实景区数据、来源和缺失信息 |
| B | 登录、交通、事件、对话、录像页面 | 经 D 提供的交通、事件、录像数据和状态 |
| C（你） | 数据、数据库、更新和资料台账 | 本文描述的全部数据基础 |
| D | FastAPI、登录、权限、HTTP 接口、历史预测 | 数据库迁移、用户/会话存储、查询函数、预测结果存储 |
| E | RAG、录像计数、短时预测 | 官方资料、授权录像、片段/计数/预测结果存储 |

特别注意：

- C 建用户和会话表，D 实现密码校验、Cookie、登录和权限。
- C 保存历史预测结果，D 负责训练和评估历史预测模型。
- C 保存知识资料与片段，E 负责解析、向量化、检索和回答。
- C 保存录像、授权和计数，E 负责 YOLO、OpenVINO、跟踪、计数和短时预测。
- A/B 不直接连接数据库，它们通过 D 的接口获取数据。

别人让你跨过这些边界时，先判断是“数据存储和来源问题”还是“页面、接口或算法问题”。你只修改 `data_foundation/`。

## 3. 数据库是什么

数据库可以先理解成“规则更严格、能互相关联的 Excel 工作簿”。

| 数据库词语 | 通俗解释 | 本项目例子 |
|---|---|---|
| 表 table | 一类东西的集合 | 景区表、来源表、客流表 |
| 行 row | 一条具体记录 | 黄山 2026 年 9 月的接待人次 |
| 字段 column | 一条记录包含的属性 | 日期、数值、单位、来源编号 |
| 主键 primary key | 每条记录唯一的编号 | 黄山的 entity_id |
| 外键 foreign key | 用编号关联另一张表 | 客流记录的 entity_id 指向黄山 |
| 唯一约束 unique | 阻止同一业务记录重复出现 | 同来源、同对象、同指标、同周期只能有一条 |
| 索引 index | 帮数据库更快找到记录 | 按对象、指标、月份查询 |
| 事务 transaction | 一组修改全部成功或全部撤销 | 同时保存客流、来源和导入记录 |
| NULL | 未知、没有提供 | 发布时间未知，不等于空字符串或 0 |

### 主键和外键示例

假设黄山的编号是 `entity-huangshan`，安徽省文旅厅来源编号是 `source-ah-wlt`：

```text
entities
id                 name   type
entity-huangshan   黄山   scenic

sources
id                 publisher
source-ah-wlt      安徽省文化和旅游厅

observations
entity_id           metric_code    period_start  value    source_id
entity-huangshan    scenic_visits  2026-09-01    1000000  source-ah-wlt
```

`observations` 不用重复写黄山的全部信息，只保存 entity_id。查询时通过这个编号找到实体表中的黄山。这就是表关系。

以上数值只是讲解结构的测试例子，不是真实业务数据，不能进入正式库。

## 4. 目前最关键的六张表

你现在先掌握下面六张，其余表知道用途即可。

### 4.1 `entities`：统计对象

存景区、火车站、机场和摄像头。

最重要字段：

- `id`：固定编号；之后不要因为改名字就换编号。
- `name`：名称。
- `type`：`scenic`、`rail_station`、`airport` 或 `camera`。
- `region_code`：所在地区。
- `longitude/latitude`：真实经纬度；没有就留空，不能猜。

它解决的问题是：“这个数属于谁？”

### 4.2 `metrics`：指标字典

存每个数字究竟表示什么。

首批五个指标：

| 代码 | 含义 | 适用对象 |
|---|---|---|
| `scenic_visits` | 景区接待人次 | 景区 |
| `rail_departures` | 铁路发送人次 | 火车站 |
| `airport_throughput` | 机场旅客吞吐量 | 机场 |
| `camera_entries` | 指定入口估计进入人次 | 摄像头 |
| `camera_exits` | 指定入口估计离开人次 | 摄像头 |

它解决的问题是：“这个数统计的是什么？”

这些指标不能相加成一个“总客流”。铁路发送人次和机场吞吐量含义不同；入口录像计数也不等于全景区在园人数。

### 4.3 `sources`：持续的数据来源

存发布单位、来源入口、使用条件、数据粒度、覆盖范围和更新频率。

例如“安徽省文化和旅游厅发布的景区统计”是一条持续来源。它不等于某个月的一篇具体公告。

它解决的问题是：“谁持续发布这类数据，使用条件是什么？”

### 4.4 `source_assets`：某一期具体原件

存某一份网页快照、PDF、表格或公告，包括文件位置、原文链接、发布时间、采集时间和文件摘要。

例如来源是“安徽省文化和旅游厅”，原件可以是“2026 年国庆假期文旅数据公告”。同一来源可以有多份原件。

它解决的问题是：“这个数字具体出自哪一份文件？”

`sources` 和 `source_assets` 的区别必须记牢：

```text
sources       = 报社/栏目
source_assets = 某天的一期报纸
```

### 4.5 `ingestion_runs`：导入批次

每执行一次检查或导入，就记录一次：什么时候开始、处理哪份原件、成功还是失败、新增多少、跳过多少、隔离多少。

它解决的问题是：“这个数字是哪一次处理放进来的？当时发生了什么？”

### 4.6 `observations`：实际观测值

存真正用于查询和画图的客流数字。

一条观测至少要说明：

- 对象 `entity_id`
- 指标 `metric_code`
- 统计起止日期
- 粒度 `day/week/month/holiday`
- 数值和单位
- 来源及具体原件
- 导入批次
- 发布时间和入库时间
- 质量状态

它解决的问题是：“哪个对象在什么时间有多少客流，证据是什么？”

### 六张表如何连起来

```text
entities ─────┐
metrics ──────┼→ observations ← sources
              │        ↑            ↑
              │  ingestion_runs     │
              │        ↑            │
              └──── source_assets ──┘
```

一条 observation 同时关联对象、指标、来源、原件和导入批次，因此可以完整追溯。

## 5. 现在必须守住的数据规则

这些规则比会写复杂 SQL 更重要。

### 规则一：没有数据不等于 0

数据库里没有 2026 年 8 月数据，应该返回“缺失”。写成 0 会让用户误以为当月完全没有游客。

### 规则二：保持来源的真实粒度

来源只发布月度总量，就存 `month`。不能把一个月的总量平均拆成四个“周数据”。这样生成的曲线看起来合理，但不是事实。

### 规则三：不同指标不能直接相加

景区接待人次、铁路发送人次和机场旅客吞吐量分别展示，不求一个总和。它们可能统计不同人群、不同次数和不同范围。

### 规则四：重复导入不能生成重复数据

同一份文件运行两次，第二次应显示新增 0。这个性质叫“幂等”。

### 规则五：来源修改数字时保留旧值

官方把 100 万修订为 102 万时，当前值更新为 102 万，但必须记录旧值、修订原件、导入批次和修改原因。这叫“修订留痕”。

### 规则六：异常不等于错误

节假日客流突然上升可能是真实情况。质量检查只能标记待复核，不能擅自删除、平滑或改成平均值。

### 规则七：所有展示值都能找到证据

数据库中的数字必须能追溯至来源、具体原件、原文位置和导入批次。无法定位的数字不能标记为 `verified`。

## 6. 你现在要会的 SQL

SQL 是向数据库提问的语言。眼下先学会读懂以下四类语句；暂时不用自己写复杂查询。

### 查看记录：`SELECT`

```sql
SELECT name, type
FROM entities
WHERE type = 'scenic';
```

含义：从实体表找出所有景区，只显示名称和类型。

### 排序：`ORDER BY`

```sql
SELECT period_start, value, unit
FROM observations
WHERE entity_id = '某个固定编号'
ORDER BY period_start;
```

含义：查某对象的观测，并按日期从早到晚排列。

### 关联表：`JOIN`

```sql
SELECT e.name, o.period_start, o.value, s.publisher
FROM observations AS o
JOIN entities AS e ON e.id = o.entity_id
JOIN sources AS s ON s.id = o.source_id;
```

含义：把观测、对象和来源连起来，查看“谁、什么时候、多少、谁发布”。

### 统计数量：`GROUP BY`

```sql
SELECT quality_status, COUNT(*)
FROM observations
GROUP BY quality_status;
```

含义：分别统计已核验、待复核和拒绝的记录数。

正式程序不让用户随便传 SQL。D/E 调用 C 提供的固定查询函数，由函数内部安全地执行参数化查询。

## 7. 四个工具分别做什么

| 工具 | 你可以怎样理解 | 项目中的职责 |
|---|---|---|
| MySQL | 数据仓库 | 真正保存表和记录 |
| SQL | 与仓库交流的语言 | 查询、增加和修改记录 |
| SQLAlchemy | Python 翻译员 | 让 Python 用模型和查询操作 MySQL |
| Alembic | 数据库结构版本管理 | 保存建表和改表步骤，让全组结构一致 |

“SQLAlchemy 模型”和“数据库表”不是两套数据。模型是 Python 对表结构的描述，最终仍由 MySQL 保存。

“迁移”也不是搬运客流数据。数据库迁移是把结构从一个版本升级到另一个版本，例如新增 `published_at` 字段。迁移文件一旦交给组员使用，后续不要直接修改旧文件，要新增下一版迁移。

## 8. 一条数据怎样进入系统

以导入一份官方月度客流表为例：

1. 在 `sources` 登记发布单位、链接、粒度和使用条件。
2. 下载或保存具体原件，计算摘要，登记到 `source_assets`。
3. 创建 `ingestion_runs`，状态为 running。
4. 解析原件，得到对象、指标、日期、数值、单位和原文位置。
5. 标准化名称、日期和单位。
6. 检查对象是否存在、指标是否匹配、日期是否合理、数值是否重复。
7. 合法数据写入 `observations`；有问题的数据进入待复核清单。
8. 更新批次为 succeeded 或 failed，并记录新增、跳过和隔离数量。
9. D 调用 C 的查询函数得到数据，再由 A/B 页面显示。

其中第 1、2、4、5、6 步需要你重点参与，因为这些步骤依赖对原始资料含义的判断。

## 9. 12 日前你必须交付什么

按团队依赖排序，首轮必须满足：

1. MySQL 可以从空库通过迁移建立结构。
2. D 能创建/查询用户，保存/查询/撤销会话。
3. D 能查询实体、指标、来源和客流时序。
4. 至少一组真实客流数据能追溯到原件和导入批次。
5. 同一文件导入两次不会重复增加观测。
6. D 能保存历史预测运行和结果；算法由 D 实现。
7. E 能登记知识资料、写入/读回片段。
8. E 能登记录像分析、写入/读回计数和短时预测结果。
9. 作业状态 `queued → running → succeeded/failed` 可以保存和查询。
10. D/E 在各自环境实际调用一次，并记录未解决问题。

前五项是最先跑通的主线，后五项是其他组员必须依赖的存储接口。真实录像还没拿到时可以用明确标记的测试数据验证接口，但不能把它说成真实资料已经交付。

## 12. 自测：能回答就可以开始做

1. `sources` 和 `source_assets` 有什么区别？
2. 为什么缺失数据不能写成 0？
3. 为什么月度数据不能拆成周数据？
4. `entity_id` 为什么不直接写景区名称？
5. 同一文件导入两次，正确结果是什么？
6. 官方修订数字后，为什么要保留旧版本？
7. 一条图表数据要通过哪些信息追溯到原文？
8. C、D、E 在登录、预测、RAG 和录像模块中分别负责什么？

参考答案：

1. source 是持续来源，asset 是某一期具体原件。
2. 缺失表示未知，0 表示确定没有发生，两者含义完全不同。
3. 拆分后的周数值不是来源发布的事实。
4. 名称可能重复或改变，固定 ID 才能稳定关联。
5. 第二次新增 0，仍保留一次检查/导入记录。
6. 保证结果可解释，并能复现旧版本使用的数据。
7. 观测 → 对象/指标 → 来源 → 具体原件/原文位置 → 导入批次。
8. C 管数据存储和来源；D 管 API、认证和历史预测；E 管 RAG、视觉计数和短时预测。

## 13. 你的最低掌握标准

在继续实现前，你不需要独立写出全部数据库代码，但应该能：

- 用自己的话解释 C 的职责边界。
- 画出六张核心表之间的关系。
- 看懂一条简单 SELECT 和 JOIN。
- 检查一份来源台账是否缺发布单位、链接、粒度、覆盖时间和使用条件。
- 判断缺失、0、月度、周度、不同指标和来源修订的区别。
- 用测试记录演示“一个数字如何找到原件和导入批次”。

达到这些标准后，你就具备推进 C 部分和参加组内对接所需的知识。开发细节可以在实际建第一版数据库时边做边学。
